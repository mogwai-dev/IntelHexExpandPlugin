Architecture note / Windows x64

Rust製WinMergeプラグインの中身

IntelHexExpandPluginを題材に、WinMergeがDLLをどう見つけ、COMオブジェクトをどう生成し、Intel HEX変換をどう呼び出すかを、言語構文ではなく境界と契約に絞って説明する。

なぜGUIDが必要なのか

短い答え: WinMergeとDLLが「どのクラスを作るのか」「そのオブジェクトがどのインターフェースを持つのか」を、名前やメモリアドレスに依存せず一致させるため。

COMではDLL名だけでは呼び出す対象が決まらない。1つのDLLが複数クラスや複数インターフェースを公開でき、表示名は変更や重複が起こり得る。そこで128 bitのGUIDを、長期間変わらない機械向け識別子として使う。

IID

IWinMergeScript

9B4C…7249
メソッド集合とvtable配置、つまり「会話の型」を識別する。

CLSID

WinMergeScript class

C6E9…C4AE
生成したい具象COMクラスを識別する。DllGetClassObjectが照合する値。

LIBID

Type Library

DCB0…4D9C
型情報一式を識別する。名前呼び出しをメソッドIDへ変換するときに使われる。

GUIDは秘密鍵ではない。 認証・暗号・ライセンスのためではなく、世界規模で衝突しにくい識別子である。同じ契約を保つ限りIIDは変更しない。互換性のないインターフェースへ変える場合は新しいIIDを割り当てる。

ソフトウェア構造

コードは実質3層で、危険なWindows FFIを外側へ寄せ、変換ロジックを通常のRustとして分離している。

Host

WinMerge

プラグインDLLを発見し、プロパティを問い合わせ、比較前にUnpackFileを呼ぶ。

Windows adapter

COM / DLL境界

lib.rs。GUID照合、クラス生成、参照カウント、BSTR変換、HRESULT返却、Type Library連携を担当。

Domain

Intel HEX変換器

intel_hex.rs。BufRead → Writeだけに依存し、レコード解析、アドレス計算、整形を担当。COMなしで単体テスト可能。

DLLロードから変換まで

01 / DISCOVERWinMergeがMergePlugins内のDLLを発見してプロセスへロード。
02 / FACTORYDllGetClassObject(CLSID, IID)で対象クラスのFactoryを要求。
03 / INSTANCEIClassFactory::CreateInstanceがWinMergeScriptを生成。
04 / CONTRACTIDispatch経由でPluginEvent、Filter、UnpackFileなどを照会。
05 / EXPAND入力・出力パスを受け取り、純粋な変換器へストリームを渡す。

DllCanUnloadNowは生存中オブジェクトが0かを返す。WinMergeはその結果を見てDLLを安全にアンロードできる。

境界で使われるインターフェース

契約役割このプラグインでの扱い
IUnknown全COMオブジェクトの基底。インターフェース照会と寿命管理。QueryInterface、AddRef、Releaseを実装。
IClassFactoryCLSIDに対応するCOMオブジェクトの生成。DLLがFactoryを返し、FactoryがWinMergeScriptを生成。
IDispatchメソッド名やDISPIDを使う動的呼び出し。埋め込みType Libraryへ名前解決と呼び出しを委譲。
IWinMergeScriptWinMergeプラグイン固有のプロパティと処理。FILE_PACK_UNPACK、対象拡張子、UnpackFileなどを公開。

ABIで受け渡す型

型意味理由
HRESULT呼び出し自体の成功・失敗コード。Windows/COM共通のエラー伝達規約。
BSTR長さを保持するUnicode文字列。ファイルパスやプラグイン情報をCOM境界で渡す。
VARIANT_BOOLCOM Automationの真偽値。Rustのboolとは表現が異なり、真は-1。
vtable関数ポインターを並べた表。Rust/C++など実装言語が違っても、同じメモリ配置と呼出規約で会話できる。

使っている技術

RUST CDYLIB

Windows DLL

crate-type = cdylibでRust固有ライブラリではなく、C ABIでロード可能なDLLを生成する。

WINDOWS-RS

Win32 / COM bindings

windows crateがGUID、BSTR、HRESULT、IDispatchなどWindows APIの型と関数を提供する。

IDL + MIDL

契約定義

IDLにインターフェース、メソッド、GUIDを記述し、MIDLがType Libraryを生成する。

TYPE LIBRARY

DLL内の型情報

build.rsがTLBをリソースとしてDLLへ埋め込む。実行時は自分自身から型情報をロードする。

REGISTRY-FREE

配置だけで導入

regsvr32やCOMレジストリ登録を使わない。WinMergeがプラグインフォルダからDLLを直接ロードする。

X64 ABI

ホストと同じアーキテクチャ

DLLはWinMergeプロセス内で動くためbit数を一致させる。このプロジェクトはx64専用。

設計上の境界

COM層は「WinMergeと会話するための翻訳機」で、Intel HEXの知識を持たせない。変換層は「Intel HEXを処理する本体」で、GUID、BSTR、HRESULTを知らない。この分離により、危険なポインター操作の範囲が限定され、変換仕様は通常のRustテストで高速に検証できる。

変更ルール: 変換仕様だけならintel_hex.rsを変更する。WinMergeとの契約を変えるならIDL、vtable、実装、Type Libraryを一組として変更し、互換性が壊れる場合は新しいIIDを発行する。
